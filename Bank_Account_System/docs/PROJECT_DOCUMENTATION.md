# Horizon Bank Account System — Project Documentation\n\n**Document ID:** HB-CAP-BAS-001 (source case study)  \n**Documentation package:** 1.0  \n**Date:** 04 October 2026  \n**Level / duration:** Beginner, five full-time days (or ten half-day sessions)  \n**Status:** Basic end-to-end service structure implemented; functional testing and operational hardening remain.\n\n## 1. Executive summary\n\nHorizon Bank's Digital Channels programme needs one API-first account service for mobile, internet banking and branch clients. Phase 1 covers account opening, balance enquiry, same-bank transfers, transfer lookup, statements and asynchronous notifications. Correctness is the primary requirement: concurrent requests, retries and component failures must not create, lose or double-count money.\n\nThe architecture is a modular monolith called `bank-account-service` plus a `notification-service` consumer. PostgreSQL 16 is authoritative for all monetary state; Redis 7 is a disposable performance/idempotency aid; Apache Kafka 4.3 carries durable domain events. The application layer selected for this package is Python 3.12+, FastAPI, psycopg 3, redis-py and confluent-kafka.\n\n## 2. Scope and stakeholders\n\n### In scope\n\n- Open a SAVINGS or CURRENT account for a new or existing customer with an initial deposit.\n- Enquire on account details and current balance.\n- Transfer INR between two Horizon accounts, with traceable reference and idempotent retries.\n- Enquire on transfer by reference.\n- Return statement totals, opening/closing balances and newest-first paginated ledger entries for at most 90 days.\n- Publish account-opened and transfer-completed events; consume them into an idempotent notification log.\n- Provide local Docker Compose infrastructure and evidence for functional, data and concurrency verification.\n\n### Out of scope for phase 1\n\nAuthentication/authorization, user interface, external-bank rails (NEFT/IMPS/UPI), cash/cheque operations, interest/fees/loans/cards, multi-currency, KYC uploads, account closure/freeze APIs, real SMS/email delivery, and cloud deployment. Security is explicitly out of scope for the training feature set, but configuration hygiene, least-privilege database access and PAN masking remain required.\n\n### Stakeholders\n\nCustomers want fast self-service; branch officers need one-call opening; operations needs traceable references and reconciliation; notification systems need asynchronous account/debit/credit facts; auditors need an immutable ledger.\n\n## 3. Goals and acceptance outcomes\n\n- Account number is returned immediately after one successful open request.\n- Every completed transfer debits and credits exactly once, in one ACID database transaction.\n- Client retries with the same `Idempotency-Key` return the original result without moving money again.\n- Account and statement reads are paginated/efficient and invalidated after a transfer.\n- Events are keyed to preserve per-account ordering and notification consumption is duplicate-safe.\n- On a fresh seed, all MUST cases pass; 20 concurrent attempts from the specified 13,500 balance produce 13 successes and 7 business rejections, with reconciliations R1–R3 empty.\n\n## 4. Business rules\n\n| ID | Rule |\n|---|---|\n| BR-01 | PAN is upper-case `AAAAA9999A`, unique customer identity. Existing PAN links to that customer; supplied profile details do not update it. |\n| BR-02 | Customer must be at least 18 on opening date. |\n| BR-03 | Email is unique/lower-case. Phone is a unique 10-digit Indian mobile beginning 6–9. Cross-customer email/phone collision is `CUSTOMER_CONFLICT`. |\n| BR-04 | Account types are SAVINGS and CURRENT; at most one of each per customer. |\n| BR-05 | Minimum initial deposit is ₹1,000 savings / ₹5,000 current; maximum ₹10,00,000. |\n| BR-06 | Account number is 12 digits: `5010` plus an 8-digit database sequence; never reused. |\n| BR-07 | Currency is INR only. |\n| BR-08 | No account balance may be negative. |\n| BR-09 | Only ACTIVE accounts may send or receive. |\n| BR-10 | Transfer is ₹1.00–₹2,00,000.00, at most two decimal places. |\n| BR-11 | Completed outgoing transfers total at most ₹5,00,000 per account per IST calendar day. |\n| BR-12 | Sender and receiver differ. |\n| BR-13 | Every transfer has an `Idempotency-Key` (1–64 allowed characters; UUID recommended); a key cannot move money twice. |\n| BR-14 | Transfer row, both balance updates and both ledger legs commit together or roll back together. |\n| BR-15 | Every balance change adds an immutable ledger entry with `balance_after`; ledger rows are never modified/deleted. |\n| BR-16 | Statement dates are ordered, not future-dated, and span at most 90 days. Defaults: last 30 days, page 0, size 20; size 1–100. |\n| BR-17 | Statement reports opening/closing balance and period credit/debit totals. |\n| BR-18 | Reference is `TRF` + `yyyyMMdd` + six-digit sequence; unique; gaps are acceptable. |\n| BR-19 | Cached balance is display-only and never authorizes a debit. |\n| BR-20 | Account opening, debit and credit notifications are emitted asynchronously within seconds. |\n\n## 5. Non-functional requirements\n\n| ID | Requirement |\n|---|---|\n| NFR-01 | Strong balance consistency: a committed transfer is visible to the next database-backed read. |\n| NFR-02 | No lost update or negative balance under 20 parallel outgoing transfers; money conserved. |\n| NFR-03 | Laptop targets: account GET p95 <50 ms cache hit / <200 ms miss; transfer p95 <300 ms. |\n| NFR-04 | Redis outage does not stop APIs; idempotency falls back to PostgreSQL unique constraint. |\n| NFR-05 | Kafka outage does not undo transfer; publish failure and payload are logged. A transactional outbox is a stretch improvement. |\n| NFR-06 | Audit path is reference → transfer row → two ledger legs → event. |\n| NFR-07 | Secrets from environment, database app role has least privilege, no full PAN in logs. |\n| NFR-08 | Correlation ID is logged per request; health endpoint checks DB, Redis and Kafka. |\n| NFR-09 | Layered controller/service/repository structure; no SQL in controllers; schema scripts are versioned. |\n| NFR-10 | A reviewer can start infrastructure with Compose and the app with one documented command. |\n\n## 6. Architecture and data flow\n\n### Components\n\n1. **REST client:** Postman, curl, branch/mobile/web clients.\n2. **API service:** request validation, correlation IDs, problem responses, business services and repositories.\n3. **PostgreSQL:** authoritative customers, accounts, transfers, append-only ledger and notification log.\n4. **Redis:** account summary cache, versioned statement cache and idempotency result keys.\n5. **Kafka:** versioned account/transfer event topics; three partitions and seven-day retention in the reference design.\n6. **Notification consumer:** builds SMS/email message text and inserts one log entry per event/account.\n\n### Transfer sequence\n\n1. Validate body and required idempotency header.\n2. Claim/replay idempotency key in Redis (database unique key is final protection).\n3. Start a PostgreSQL transaction; set a short lock timeout; lock both account rows in ascending `account_id` order.\n4. Verify accounts exist and are ACTIVE, amount is affordable, daily outgoing limit remains satisfied.\n5. Insert transfer, update sender and receiver balances, add DEBIT and CREDIT ledger rows.\n6. Commit once; any error before commit rolls back every monetary write.\n7. After commit, evict both account cache entries, increment both statement versions, store replay response, publish `TransferCompleted` keyed by sender account.\n8. Respond with the transfer reference and sender balance after transfer.\n\nRedis and Kafka calls must not occur inside the money transaction. A Kafka publish failure does not roll back committed money. Document this commit/publish gap; an outbox is the robust extension.\n\n### Account opening sequence\n\nIn one PostgreSQL transaction: find/upsert customer by PAN without overwriting an existing profile, create account, append initial CREDIT ledger entry. After commit publish `AccountOpened`, keyed by account number. First account enquiry fills Redis.\n\n### Statement sequence\n\nValidate date/paging inputs in IST; verify account exists. Resolve statement version, fetch cache entry; on miss calculate period opening/closing balances, totals, count and newest-first page from PostgreSQL, cache the response for five minutes.\n\n## 7. PostgreSQL model\n\nUse exact `NUMERIC(15,2)` amounts throughout. Store instants as `TIMESTAMPTZ`; apply `Asia/Kolkata` for business-day and statement boundaries. Database constraints complement API checks. Expose business keys, not surrogate IDs.\n\n### Entities\n\n- **customer:** `customer_id` identity PK; name, lower-case unique email, unique Indian phone, DOB, unique PAN, created timestamp.\n- **account:** `account_id` identity PK (also global row-lock order); unique generated account number, customer FK, account type, INR currency, nonnegative balance, status, version, opened/updated timestamps. Unique `(customer_id, account_type)`.\n- **fund_transfer:** UUID PK; unique generated reference; unique idempotency key and request fingerprint (binds a retry key to its original request body); sender/receiver account FKs; positive amount; optional remarks; status/failure reason; created timestamp. Sender and receiver must differ.\n- **account_transaction:** identity PK; account FK; optional transfer FK; CREDIT/DEBIT, positive amount, nonnegative `balance_after`, description and transaction timestamp. Unique `(transfer_id, txn_type)`; initial deposit has null transfer ID. Append-only.\n- **notification_log:** composite key `(event_id, account_number)`; event type, channel, message and created timestamp. Consumer uses conflict-ignore for deduplication.\n\n### Indexes and integrity\n\nIndex account number/PAN/email/phone unique keys; outgoing transfer `(from_account_id, created_at)` for daily limit; statement ledger `(account_id, txn_time DESC, txn_id DESC)`; transfer reference; ledger transfer/type uniqueness. Include checks for PAN, phone, account status/type/currency, positive transfer/ledger amounts and nonnegative account/ledger balances. Restrict the application login (`bank_app`) from DDL, ledger UPDATE/DELETE and unnecessary privileges; use admin only for schema setup.\n\n### Reconciliation invariants\n\nAfter transfer and concurrency scenarios, run the supplied/implemented reconciliation checks:\n\n- R1: account current balance agrees with the sum of its ledger movements.\n- R2: every completed transfer has exactly one equal-amount DEBIT and one equal-amount CREDIT, attached to the right accounts.\n- R3: total balances are conserved by each completed internal transfer and no account is negative.\n\nThe reconciliation queries are included in db/03_reconciliation.sql.\n\n## 8. Redis design\n\nAll keys use `bank:<entity>:<business-id>...`; key names live in one cache-key module. Every data cache key expires.\n\n| Key | Type/value | TTL and behavior |\n|---|---|---|\n| `bank:account:{no}` | Hash: account number, customer name, type, currency, balance, status, openedAt | 600 s; cache-aside. Evict after committed transfer. |\n| `bank:stmt-ver:{no}` | Integer string, missing means 0 | Increment after every affected account transfer. |\n| `bank:stmt:{no}:v{ver}:{from}:{to}:{page}:{size}` | Full statement JSON | 300 s. Old versions expire naturally. |\n| `bank:idem:{key}` | `PENDING` then response JSON | 86,400 s. Claim with SET NX; replay saved response; clean abandoned claims safely. |\n| `bank:rl:{no}:{minute}` | Per-minute request count (optional stretch) | 60 s. |\n\nIf Redis is unavailable, account and statement APIs read PostgreSQL. A committed transfer still relies on the unique database idempotency key to prevent duplicates.\n\n## 9. Kafka contracts\n\nTopic names are lower-case, dot-separated and versioned:\n\n- `bank.account.opened.v1` — key is account number.\n- `bank.transfer.completed.v1` — key is sender account number.\n- `bank.transfer.failed.v1` — optional stretch only.\n\nReference setup uses Kafka 4.3.1 in KRaft mode, three partitions, seven-day retention, no automatic topic creation. Producer uses acknowledgements `all` and idempotent publishing. Event amounts are strings to prevent floating-point errors.\n\n### Envelope\n\n```json\n{\n  "eventId": "UUID",\n  "eventType": "TransferCompleted",\n  "eventVersion": 1,\n  "occurredAt": "ISO-8601 timestamp with offset",\n  "source": "bank-account-service",\n  "correlationId": "request correlation ID",\n  "data": {}\n}\n```\n\n`AccountOpened` data includes account number, customer ID/name, type, currency, initial deposit string and contact details. `TransferCompleted` contains transfer/reference IDs, sender/receiver account numbers, amount string, currency and remarks. Consumer group `notification-service` inserts one notification row per affected account with `ON CONFLICT (event_id, account_number) DO NOTHING`; replay is therefore harmless.\n\n## 10. REST API specification\n\nBase path: `/api/v1`. JSON content type. Amounts are decimal strings with two fractional digits; timestamps are ISO-8601 with offset. Generate or propagate `X-Correlation-Id` on every response/log path.\n\n### `POST /accounts` — MUST\n\nRequest: `customer` object (`fullName`, `email`, `phone`, `dateOfBirth`, `pan`), `accountType`, `initialDeposit`. PAN is uppercased; email lowercased. Validate age, phone, email and deposit range/minimum. Success is `201 Created`, `Location` points to the new account, response includes `accountNumber`, `customerId`, `customerName`, `newCustomer`, type, currency, balance, status and `openedAt`.\n\nErrors: `400 VALIDATION_ERROR`; `409 DUPLICATE_ACCOUNT_TYPE` or `CUSTOMER_CONFLICT`.\n\n### `GET /accounts/{accountNumber}` — MUST\n\nReturns account number, customer name, account type, currency, balance, status and openedAt. `X-Cache: MISS|HIT`. Invalid format is 400; missing account is 404 `ACCOUNT_NOT_FOUND` and is not cached.\n\n### `POST /transfers` — MUST\n\nRequired header `Idempotency-Key` (1–64 allowed characters). Body: `fromAccountNumber`, `toAccountNumber`, decimal-string `amount`, optional `remarks` (≤100 chars). Success `201 Created`, `Location` points to transfer enquiry. Include transfer ID, reference, status, accounts, amount, currency, remarks, sender `fromBalanceAfter`, createdAt. Same key/body replay returns original body and `Idempotent-Replayed: true` without another movement.\n\nErrors: 400 `VALIDATION_ERROR` / `MISSING_IDEMPOTENCY_KEY`; 404 `ACCOUNT_NOT_FOUND`; 409 `REQUEST_IN_PROGRESS`; 422 `SAME_ACCOUNT_TRANSFER`, `ACCOUNT_NOT_ACTIVE`, `INSUFFICIENT_FUNDS`, `DAILY_LIMIT_EXCEEDED`; 503 `SERVICE_BUSY` with `Retry-After: 1` for lock timeout/deadlock.\n\n### `GET /transfers/{referenceNo}` — SHOULD\n\nReturn transfer details by reference, omitting `fromBalanceAfter` to avoid disclosing current/historical balance. Unknown reference: 404 `TRANSFER_NOT_FOUND`.\n\n### `GET /accounts/{accountNumber}/statement` — MUST\n\nQuery: `fromDate`, `toDate`, `page`, `size`. Defaults are IST today minus 29 days through today, page 0, size 20. Date range max 90 days; end date cannot be future. Response includes account/customer/currency, date range, opening/closing balances, credits/debits, page/size/totalElements/totalPages and newest-first transaction records. `X-Cache: MISS|HIT`. Bad parameters return 400; unknown account 404.\n\n### `GET /health` or `/actuator/health`\n\nHealth response reports the application and PostgreSQL, Redis and Kafka connectivity.\n\n### Error response\n\nUse `application/problem+json` following RFC 9457, extended with `errorCode`, `correlationId`, timestamp and validation `errors` list. Never expose SQL, stack traces, table/constraint names or another customer's balance.\n\n## 11. Security, resilience and operations\n\n- Local example passwords are deliberately simple and must never be reused outside this training stack.\n- Commit `.env.example`, never `.env`; read configuration only from environment.\n- Use `bank_app` at runtime, never admin. The sample Compose file creates the admin login; a schema/bootstrap script must create the least-privilege application role and tables.\n- Mask PAN; do not include full PAN in logs or responses. Do not return recipient balance in transfer enquiry.\n- Redis values are expendable; PostgreSQL remains the source of truth. Timeouts ensure Redis/Kafka outages do not hold API requests indefinitely.\n- Kafka publishing after commit has a crash gap. Log failed payload and document manual recovery; transactional outbox is the recommended stretch design.\n- Health check should report each dependency; structured logs include correlation ID and stack traces stay server-side.\n\n## 15.
